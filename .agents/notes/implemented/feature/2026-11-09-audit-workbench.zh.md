# Agent Note: 审计工作台读取插件包与项目档案

Status: implemented

[English](2026-11-09-audit-workbench.md) | 中文

## 问题

桌面端审计模式打开的是对话视图，同时进行几个审计项目的用户只有逐个打开会话，才能知道哪些外部系统还需要登录、有哪些审计项目、各项目的开工任务进行到哪一步。这些信息已经存在于本仓库不拥有的两处：私有的审计插件包，其服务知道各系统的登录状态；以及插件包的 audit-issue-workflow 技能在每个项目目录中写入的项目档案 `审计方案/00_项目档案.json`。本 fork 是公开的，插件包是私有的，因此 fork 不能携带插件包的系统清单、工具名或提示词。

## 决策

审计工作台页面分为 Host 包 [`dsh-audit-workbench`](../../../../packages/audit/audit-workbench/README.zh.md) 和浏览器包 [`dsh-client-ui-audit-workbench`](../../../../packages/client/ui-audit-workbench/README.zh.md)，两者都挂载在 `audit-desktop` profile 的根上。

- **页面显示的内容由插件包声明。** 插件包的 `package.json` 在 `dsh.auditWorkbench` 中给出工作台清单；清单列出各系统及其会话工具和登录工具、内置模型和提示词模板。fork 中没有任何系统 id、工具名或提示词文本。
- **登录状态来自各系统自己的工具。** 检查时在任何会话之外，按插件包 MCP 客户端行解析出的启动参数启动该系统的服务，调用清单中的会话工具，并比较结果中的一个字段。登录时调用该系统自己的登录工具。每个系统只有一处登录，即其服务原有的登录。
- **启动参数取自插件包的行。** Host 行以带前缀的 id 重新挂载插件包的 `audit-toolkit` 分组，并把每条 stdio MCP 客户端行改写为启动参数插件，因此 loader 计算插件包自己的表达式，也不会注册任何模型工具。
- **项目档案只读。** 页面显示本读取器已知的字段，并在档案高于已知档案版本时加以说明；只有审计会话的主 agent 写入项目档案。
- **提示词只展示，不发送。** 操作在 Host 上填充模板，展示给用户，并新开一个会话，把提示词放进输入框；由用户发送。

## 考虑过的替代方案

**在 fork 中写死系统和提示词。** 插件包按自己的节奏发布，内容是私有的，这样插件包的每次改动都需要改 fork，而且公开的 fork 会暴露插件包的内部内容。

**复用运行中会话的 MCP 客户端。** 概览页没有会话，而会话的客户端会注册模型可见的工具；页面上的检查就会取决于打开的是哪个会话。一次性启动服务的代价是每次检查都要启动一次服务。

**在档案旁另存工作台状态文件。** 另一份记录项目进度的文件会有两个写入方，并与技能维护的档案产生偏差；直接读取档案可以使每个项目只有一份记录。

**自动发送提示词。** 启动开工任务或内置模型会代表用户访问外部系统；先展示提示词，用户可以在任何模型请求之前调整被审计单位、期间或范围。

## 后果

页面适用于任何附带清单的插件包，插件包没有清单时只显示项目档案。启动后的第一次检查要等待服务的 Python 环境，会话中的服务是另外的进程。清单格式和档案字段是本仓库与插件包之间的接口：插件包改名会话工具或结果字段时只需修改清单，而新增的档案字段要等本读取器支持后才会在页面上显示。
